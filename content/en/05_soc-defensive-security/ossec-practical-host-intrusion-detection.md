# OSSEC: host-based intrusion detection, log analysis and active response

OSSEC is a **HIDS - Host Intrusion Detection System**.

Its purpose is not to capture network packets like a classic NIDS, but to observe what is happening directly on monitored hosts.

It can analyze, among other things:

- system and application logs,
- authentication events,
- file changes,
- checksums,
- processes and operating system state,
- newly created accounts,
- service activity,
- rootkit indicators,
- security events generated by applications.

The most important part is not log collection itself.

OSSEC tries to answer one question:

> **Which events among thousands of normal logs may indicate real attacker activity?**

That is why **decoders and detection rules** are at the core of the system.

---

# Mental model

The easiest way to understand OSSEC is as a pipeline:

```text
HOST
  │
  ▼
LOG
  │
  ▼
DECODER
  │
  ▼
RULE
  │
  ▼
ALERT
  │
  ├──► analyst
  │
  ├──► e-mail / Slack / SIEM
  │
  └──► Active Response
             │
             ▼
       automated action
```

For example, an application may generate:

```text
192.168.1.44 GET /security
```

By itself, this is just text.

A decoder may transform it into:

```text
src_ip = 192.168.1.44
method = GET
url = /security
```

Only then can a rule assign security meaning:

```text
IF url == "/security"
THEN generate level 10 alert
```

The fundamental transformation is:

```text
raw event
    ↓
structured information
    ↓
security context
```

That is the basis of how OSSEC works.

---

# Architecture

A typical deployment consists of a central OSSEC server and agents installed on monitored endpoints.

```text
                    ┌─────────────────┐
                    │   OSSEC Server  │
                    │                 │
                    │ decoders        │
                    │ rules           │
                    │ correlation     │
                    │ alerts          │
                    │ active response │
                    └────────┬────────┘
                             │
             ┌───────────────┼───────────────┐
             │               │               │
             ▼               ▼               ▼
        Linux Agent     Windows Agent    Linux Agent
             │               │               │
         syslog          Event Logs        auth.log
         auth.log        PowerShell        syslog
         files           Security          files
```

The agent observes the local host and sends telemetry to the central server.

The server then:

```text
collects
   ↓
decodes
   ↓
matches rules
   ↓
correlates
   ↓
alerts
   ↓
optionally responds
```

OSSEC can also operate in an **agentless** mode.

This is useful for devices where a normal agent cannot be installed, such as:

```text
switch
router
firewall
hypervisor
network appliance
```

---

# HIDS, not NIDS

This distinction matters.

A NIDS primarily observes:

```text
network traffic
```

A HIDS observes:

```text
host activity
```

OSSEC may receive information about network activity through host logs, but it does not behave like a passive sensor capturing all packets from a switch.

That means tools such as:

```text
Suricata
Snort
Zeek
Wireshark
```

are not direct replacements for OSSEC.

They can complement it.

A defensive architecture may look like this:

```text
NETWORK                    HOST
   │                         │
   ▼                         ▼
Suricata / Zeek           OSSEC
   │                         │
   └──────────┬──────────────┘
              ▼
          SIEM / ELK
              │
              ▼
           Analyst
```

Each layer sees a different part of the attack.

# The OSSEC directory

In a standard installation, one of the most important locations is:

```text
/var/ossec/
```

Most of the OSSEC infrastructure is stored there.

A useful mental map is:

```text
/var/ossec/
│
├── bin/        executables and management tools
├── etc/        configuration
├── logs/       logs and alerts
├── rules/      detection rules
├── queue/      internal communication
└── var/        runtime information
```

The primary configuration file is:

```text
/var/ossec/etc/ossec.conf
```

It is the central configuration point of the system.

---

# Logs that matter

During analysis, two categories of logs should be distinguished.

## ossec.log

```text
/var/ossec/logs/ossec.log
```

This describes what OSSEC itself is doing.

If:

```text
rule does not load
decoder is broken
agent cannot connect
configuration contains an error
```

this is one of the first places to check.

## alerts.log

```text
/var/ossec/logs/alerts/alerts.log
```

This is where security alerts are stored.

These are events that matched OSSEC rules.

Mental model:

```text
ossec.log
    =
what is happening with OSSEC

alerts.log
    =
what OSSEC thinks is happening in the monitored environment
```

---

# Decoders

For OSSEC, an application log initially exists only as text.

Example:

```text
10.10.10.23 GET /security HTTP/1.1
```

Before a meaningful detection rule can be created, the structure of this event has to be understood.

That is the job of a **decoder**.

A decoder may extract fields such as:

```text
src_ip
dst_ip
src_port
dst_port
protocol
method
url
user
action
status
```

The process becomes:

```text
RAW LOG

10.10.10.23 GET /security HTTP/1.1

        ↓ decoder

src_ip = 10.10.10.23
method = GET
url = /security
```

This allows OSSEC to work with proprietary applications generating custom log formats.

That is especially important in environments containing:

```text
legacy applications
CRM
ERP
accounting software
custom internal systems
proprietary applications
```

If an application produces logs, a decoder can potentially be created for them.

---

# Custom detection

A decoder answers:

> **What is inside the log?**

A rule answers:

> **What does it mean from a security perspective?**

Consider:

```text
GET /security
```

This may represent an attempt to access a hidden or sensitive resource.

A rule could therefore define:

```text
decoded_as = security-access
url = security
level = 10
```

The complete pipeline becomes:

```text
request
   ↓
access.log
   ↓
custom decoder
   ↓
URL extracted
   ↓
custom rule
   ↓
level 10 alert
```

In this way, even a simple application endpoint can become a **tripwire**.

---

# Local rules

One of the most important OSSEC administration rules is:

> **Do not directly modify vendor-provided default rules.**

Custom logic should be stored in local rules.

A typical location is:

```text
local_rules.xml
```

The reason is simple.

During an update:

```text
default rules
        ↓
may be replaced
```

Any direct modifications may be lost.

The correct mental model is:

```text
vendor rules
    =
read / use

local rules
    =
customize
```

The material also uses the convention of assigning custom rules identifiers above:

```text
100000
```

to reduce the risk of conflicts with built-in rules.

---

# Overwriting existing rules

Sometimes a built-in rule is good enough, but its severity level is too low.

For example:

```text
existing rule
level = 3
```

while the organization considers the event important enough to be:

```text
level = 7
```

Instead of directly editing the original rule, OSSEC can use:

```text
overwrite
```

This allows local tuning while keeping vendor rules intact.

That is particularly useful when adjusting rule severity without risking losing changes during updates.

---

# Alert levels

OSSEC assigns its own severity levels to events.

The range goes up to:

```text
0 → 15
```

Conceptually:

```text
LOW                                      HIGH

0 ────────────────────────────────────── 15

noise
information
suspicious activity
security event
attack
critical event
```

Not every log should become an incident.

If a system generates alerts for everything:

```text
everything becomes an alert
        ↓
analyst receives noise
        ↓
real attacks disappear inside noise
```

This is why **tuning** is one of the most important parts of deployment.

The training material suggested beginning analysis around:

```text
level 5–6
```

and using higher levels for more significant events.

This is not a universal threshold.

Severity always depends on the environment.

---

# Detection engineering mindset

OSSEC demonstrates one of the fundamental principles of defensive engineering.

Do not begin with:

> What rule should I write?

Begin with:

```text
What does the attack change?
```

Then ask:

```text
Where can I observe it?
```

Then:

```text
What log contains the evidence?
```

Only then move to:

```text
How do I decode it?

How do I detect it?

How do I respond?
```

The full chain is:

```text
ATTACK
   ↓
ARTIFACT
   ↓
LOG
   ↓
DECODER
   ↓
RULE
   ↓
ALERT
   ↓
RESPONSE
```

This way of thinking remains valid regardless of whether the final platform is:

```text
OSSEC
Wazuh
Splunk
Elastic
Microsoft Sentinel
QRadar
```

---

# Testing rules

A rule that has never been tested is not yet a reliable detection.

A proper workflow should look similar to:

```text
sample log
    ↓
decoder test
    ↓
rule test
    ↓
configuration reload
    ↓
generate real event
    ↓
check alerts.log
```

After configuration changes, a restart may be required:

```bash
/var/ossec/bin/ossec-control restart
```

Then check:

```text
ossec.log
```

and:

```text
alerts.log
```

A configuration that loads successfully does not automatically mean the detection behaves correctly.

---

# Agents

Agents are OSSEC's eyes on monitored endpoints.

They can observe:

```text
Linux logs
Windows Event Logs
PowerShell logs
Application logs
file changes
authentication activity
system changes
```

A Windows agent may collect channels such as:

```text
Application
Security
System
Windows PowerShell
```

Each agent must also be associated with the OSSEC server.

Providing only the server IP address is not enough.

An individual authentication key is used as well.

This allows the server to understand:

```text
which endpoint
generated
which event
```

Agent availability is also useful during forensic analysis.

If an endpoint was:

```text
last seen: 02:18
```

and stopped communicating afterwards, that timestamp may become an important part of the incident timeline.

---

# File Integrity Monitoring

One of OSSEC's major capabilities is **File Integrity Monitoring - FIM**.

The idea is straightforward.

```text
FILE
  │
  ▼
HASH
  │
  ▼
baseline
  │
  ▼
file changes
  │
  ▼
new hash
  │
  ▼
ALERT
```

This can help identify:

```text
modified system binaries
changed configuration
new files
web shells
malware persistence
unexpected scripts
tampering
```

Default monitoring focuses on important system paths such as:

```text
/etc
/usr/bin
/usr/sbin
/bin
/sbin
/boot
```

But these paths should not be treated as a complete monitoring strategy.

---

# Monitor what an attacker would use

One of the most important defensive lessons is that attackers often use locations defenders classify as unimportant or noisy.

Examples include:

```text
/tmp
C:\Windows\Temp
C:\Windows\Prefetch
```

These directories change frequently, so excluding them may reduce noise.

But malware may use those same locations.

This creates a trade-off:

```text
less monitoring
      =
less noise

but

less monitoring
      =
larger detection blind spot
```

Every:

```text
ignore
exclude
whitelist
```

should therefore be treated as a potential **blind spot**.

From a Purple Team perspective, this is especially important.

Red Team asks:

```text
where is the defender not looking?
```

Blue Team should ask:

```text
what could an attacker hide here?
```

---

# New files matter

Detection of newly created files can be particularly valuable.

For example, on a web server:

```text
/var/www/
```

the sudden appearance of:

```text
shell.php
cmd.php
upload.php
backdoor.js
```

may provide a much stronger signal than the original HTTP request.

This is why defenders should monitor not only:

```text
request
```

but also:

```text
resulting state change
```

An attack may look unremarkable in HTTP logs but create a highly suspicious filesystem artifact.

---

# Rootkit detection

OSSEC also provides rootkit detection mechanisms.

The concept is similar to YARA.

A known rootkit may leave a characteristic artifact:

```text
specific file
specific filename
specific path
specific registry entry
specific system modification
```

A detection can therefore follow:

```text
IF artifact exists
THEN rootkit suspicion
```

For example:

```text
/tmp/fake.ai
     ↓
matches known rootkit artifact
     ↓
rootcheck
     ↓
alert
```

A single artifact does not automatically prove compromise.

It is an **indicator** that must be interpreted in context.

---

# YARA analogy

A useful way to understand OSSEC is to compare it with YARA.

YARA:

```text
FILE
  ↓
PATTERN
  ↓
MATCH
  ↓
MALWARE INDICATOR
```

OSSEC:

```text
LOG
  ↓
DECODER
  ↓
RULE
  ↓
SECURITY INDICATOR
```

Both systems rely on recognizable patterns.

The main difference is the data source.

YARA commonly analyzes:

```text
files
memory
binary artifacts
```

OSSEC focuses primarily on:

```text
logs
host activity
filesystem changes
system events
```

---

# Active Response

A HIDS traditionally focuses on:

```text
detect
```

OSSEC can also:

```text
respond
```

This mechanism is called **Active Response**.

For example:

```text
SSH brute force
      ↓
authentication failures
      ↓
OSSEC rule
      ↓
level 7 alert
      ↓
Active Response
      ↓
firewall-drop
      ↓
source IP blocked
```

The training material demonstrated actions such as:

```text
host-deny
firewall-drop
disable-account
```

Blocking can also be temporary, for example:

```text
600 seconds
```

This allows OSSEC to behave partially like a HIPS.

---

# Active Response is just automation

There is no hidden magic behind Active Response.

For example:

```text
firewall-drop
```

is simply a script performing an operating system action.

Conceptually:

```text
ALERT
   ↓
COMMAND
   ↓
SCRIPT
   ↓
OS ACTION
```

On Linux, this may result in adding a firewall rule blocking the source address.

Custom responses can therefore be created, such as:

```text
isolate host
disable account
kill process
block IP
notify SOC
create ticket
send webhook
collect forensic artifact
```

At that point OSSEC becomes not only a detection engine but also a simple response automation platform.

---

# The danger of automatic response

Automatic response can be effective, but poor configuration may create new problems.

Imagine:

```text
level 3
      ↓
common false positive
      ↓
firewall-drop
```

A legitimate user may be blocked automatically.

That is why Active Response should normally depend on detections with sufficient confidence.

Mental model:

```text
low confidence
    ↓
observe

medium confidence
    ↓
alert

high confidence
    ↓
respond
```

The more destructive the response, the higher the confidence threshold should be.

---

# Brute-force detection

Authentication logs are one of the most natural data sources for OSSEC.

A single event:

```text
authentication failed
```

does not automatically mean an attack.

It may simply be a user entering the wrong password.

But a sequence such as:

```text
failure
failure
failure
failure
failure
```

within a short period may indicate:

```text
brute force
```

This illustrates the difference between:

```text
event detection
```

and:

```text
behavior detection
```

A more difficult case is:

```text
slow brute force
```

where the attacker intentionally spaces attempts over time.

This is why security monitoring should not rely solely on individual events.

---

# Web attack detection

OSSEC can also analyze web server logs.

Typical sources include:

```text
Apache access.log
Apache error.log
Nginx access.log
Nginx error.log
```

Possible detection logic may cover:

```text
suspicious URLs
scanner activity
authentication attacks
server errors
unexpected HTTP methods
known exploit patterns
```

An interesting defensive technique is creating a resource that legitimate users should never access.

For example:

```text
/admin-backup-secret/
```

Any access attempt may then generate a high-severity alert.

This creates a simple **honeypot / tripwire mechanism**.

---

# Detecting scanners

Automated tools such as:

```text
feroxbuster
ffuf
gobuster
nmap
```

often generate recognizable activity.

However, a rule such as:

```text
User-Agent == feroxbuster
```

is not a robust detection strategy.

The User-Agent can easily be changed.

Better indicators may include:

```text
large number of requests
many nonexistent paths
specific request frequency
access to trap endpoints
repeated 404/403 responses
```

Instead of focusing on:

```text
tool detection
```

it is usually better to focus on:

```text
behavior detection
```

---

# Integrations

OSSEC can forward its results to other systems.

For example:

```text
OSSEC
  │
  ├──► email
  ├──► Slack
  ├──► Syslog
  └──► JSON
         │
         ▼
      Filebeat
         │
         ▼
      Logstash
         │
         ▼
   Elasticsearch
         │
         ▼
       Kibana
```

This allows the environment to separate:

```text
detection engine
```

from:

```text
storage
visualization
analytics
```

OSSEC does not need to function as a complete SIEM.

It can serve as a high-quality source of host-based security events.

JSON output makes downstream processing easier.

Conceptually:

```text
OSSEC alert
      ↓
JSON
      ↓
Filebeat
      ↓

      ↓
Elasticsearch
      ↓
Kibana
```

This enables:

```text
dashboards
statistics
timelines
search

```

OSSEC can therefore focus primarily on:

```text
host visibility
+
detection
```

while Elastic handles:

```text
search
+
storage
+
visualization
```

# OSSEC vs Security Onion

They should not be treated as identical solutions.

OSSEC is relatively lightweight and host-focused.

Security Onion is a much larger ecosystem and may combine endpoint and network visibility.

Conceptually:

```text
OSSEC

lightweight
host focused
log based
FIM
active response
rootkit detection
```

versus:

```text
Security Onion

network visibility
IDS
Zeek
Suricata
endpoint telemetry
search
correlation
large data pipeline
```

The right question is not:

> Which one is better?

The right question is:

> Which one fits the architecture and visibility requirements of the environment?

The underlying concepts remain similar:

```text

rules
```

```text
dashboards

management
```

# Attacker perspective

OSSEC should also be understood from a Red Team perspective.

If an attacker learns:

```text
what is monitored
what is ignored
which paths trigger alerts
which actions trigger Active Response
```

they may attempt to operate outside monitored areas.

For example:

```text
/tmp ignored
```

may suggest:

```text
good staging directory
```

while:

```text
/var/www monitored in real time
```

may mean:

```text
web shell may trigger FIM
```

A useful defensive question is therefore:

> **If I were the attacker and knew this monitoring configuration, where would I try to hide?**

---

# Defender perspective

From a Blue Team perspective, OSSEC is primarily about increasing visibility.

The goal is not to collect every possible log.

The goal is to detect meaningful changes.

Good monitoring should help answer:

```text
Who authenticated?

From where?

What changed?

Which file appeared?

Which process started?

Which service failed?

Was a new account created?

Was a protected resource accessed?

Did an endpoint suddenly disappear?

Was the same action repeated?

Does the event match known malicious behavior?
```

These small observations eventually form the full picture of an incident.

---

# Practical hardening checklist

When deploying OSSEC, pay particular attention to:

```text
[ ] monitor critical system directories
[ ] monitor temporary directories where appropriate
[ ] enable detection of new files
[ ] reduce excessive FIM intervals
[ ] collect authentication logs
[ ] collect PowerShell and Windows security logs
[ ] monitor webserver logs
[ ] create custom decoders for proprietary applications
[ ] keep custom rules separate from vendor rules
[ ] test every custom decoder and rule
[ ] tune alert levels
[ ] review ignored paths
[ ] configure Active Response conservatively
[ ] protect communication between agents and server
[ ] restrict access to the OSSEC server
[ ] forward important alerts to central monitoring
[ ] monitor agent availability
```

---

# What to investigate first

When OSSEC generates a high-severity alert, do not stop at the rule description.

Pivot further.

```text
ALERT
  │
  ├──► source IP
  │
  ├──► destination
  │
  ├──► user
  │
  ├──► process
  │
  ├──► file
  │
  ├──► surrounding logs
  │
  ├──► previous events
  │
  └──► events after detection
```

An alert is the beginning of an investigation, not the end.

# Analyst workflow

Example investigation:

```text
OSSEC ALERT
"authentication failed"
        │
        ▼
Which user?
        │
        ▼
Which source IP?
        │
        ▼
How many attempts?
        │
        ▼
Was there later a successful login?
        │
        ▼
What happened after login?
        │
        ▼
New process?
New account?
File modification?
Network connection?
```

The most interesting sequence is often not:

```text
100 failed logins
```

but:

```text
20 failed logins
        ↓
1 successful login
        ↓
new process
        ↓
new file
        ↓
outbound connection
```

That begins to tell the story of the attack.

# Field note

OSSEC is a good example of an important principle:

Detection does not begin with a dashboard.

It begins with understanding:

```text
what happened
```

then:

```text
what artifact was created
```

then:

```text
where that artifact is visible
```

and only then:

```text
how to detect it automatically
```

The GUI may change.

The SIEM may be replaced.

The dashboard may look completely different.

The fundamental pipeline remains:

```text
telemetry
   ↓
parsing
   ↓
normalization
   ↓
detection
   ↓
correlation
   ↓
alert
   ↓
response
```

If you understand this process through OSSEC, it becomes much easier to understand Wazuh, Elastic, Splunk, Sentinel, and detection engineering in general.
